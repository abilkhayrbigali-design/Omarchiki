# Требования кейса (регламент)

Источник: [case/FIN_CASE.pdf](case/FIN_CASE.pdf). При расхождении главнее кейс, затем опубликованные организаторами определения проверок, затем этот файл.
Коды требований (`E04`, `S08` и т. п.) используются в названиях тестов и в описаниях изменений.

## 1. Формат и сроки

- Онлайн-отбор 19–22 ноября 2026, команды 2–4 человека.
- Сдача до **22 ноября 2026, 23:59 по Астане (UTC+5)**. Канал сдачи организаторы сообщат отдельно.
- В финал проходят 7 лучших команд трека FinTech. Финал офлайн в Астане, предварительно 28–29 ноября.

## 2. Как оценивают — 100 баллов

Жюри оценивает корректность среды и оценщика, а не награду нашего агента.

| Код | Критерий | Баллы | Как считают | Чем закрываем |
|---|---|---|---|---|
| K1 | Контракт и изоляция | 25 | 25 × пройдено / 20 фиксированных проверок: reset/step, схемы, лимиты, завершение, неверный ввод, отсутствие утечек | `tests/contract`, `tests/leak` |
| K2 | Данные и эталон | 25 | 25 × корректных / 20 закрытых эпизодов: равенства до ошибки, объявленное расхождение после, независимая достаточность доказательств | независимый решатель + прогон по тысячам seed |
| K3 | Надёжность награды | 25 | 25 × пройдено / 20 проверок: сопоставление, чистые случаи, FP, дубли, стоимость шагов, атакующие ответы | `tests/reward` |
| K4 | Воспроизводимость и обобщение | 15 | 15 × пройдено / 20 парных проверок: повтор seed и действий точен; перестановка и смена ID сохраняют ответ oracle и награду | `tests/repro`, слой представления |
| K5 | Инженерия и объяснение | 10 | пять пунктов по 0/1/2: запуск одной командой, версии конфигураций, журналы траекторий, измеренный разбор сбоев, честные ограничения | `make check`, `configs/`, отчёт, записка |

**Блокируют оценивание:** утечка закрытых данных, запись в оценщик, реальные финансовые данные, неработающее ядро.

**Как проверяют.** На каждой среде запускают четыре политики организаторов: случайный исследователь с фиксированным seed, простой алгоритм сверки, атака «пометить всё», oracle. Все работают на 20 скрытых эпизодах, из них 5 чистых и 5 со взаимодействующими ошибками. Ещё 20 парных проверок меняют порядок и ID. Скрыты только seed и значения; типы ошибок известны заранее.

Баллов **не дают**: UI, обучение весов, высокая награда oracle сама по себе.

## 3. Требования

### Суть (раздел 01)
| Код | Требование |
|---|---|
| C01 | Это среда для возможного дообучения модели, а не платёжное приложение, чат-бот или один аудиторский отчёт |
| C02 | Обязательны интерфейс для RL, записанные траектории и оценка качества |
| C03 | Обучение весов необязательно и не должно зависеть от платных API или GPU |
| C04 | Нельзя заявлять об улучшении модели без контролируемого сравнения на отложенных данных |

### Генератор (раздел 02)
| Код | Требование | Критерий |
|---|---|---|
| G01 | Минимум четыре независимо настраиваемых типа ошибок: дубли счетов; пропущенное или частичное распределение платежа; неверная дата или курс конвертации; ошибка отнесения к отчётному периоду | K2 |
| G02 | Минимум два сценария взаимодействующих ошибок | K2 |
| G03 | Чистые компании и правдоподобные корректные отвлекающие случаи: разбитые платежи, возвраты, законные повторяющиеся суммы | K2, K3 |
| G04 | Сначала согласованная скрытая история компании, затем документы и ошибки с записанным причинным изменением | K2 |
| G05 | Эталон описывает реальное расхождение и доступные доказательства. Нельзя требовать недоступный факт | K2 |
| G06 | Варьируются имена, ID, порядок, суммы, валюты, часовые пояса, сочетания ошибок | K4 |
| G07 | Сложность требует анализа доказательств и мешает простым трюкам, но не делает задачу неразрешимой. Противоречивые данные сложностью не считаются | K2 |

| Код | Требование | Критерий |

| D04 | `ledger.csv`: `row_id, timestamp, account, debit_minor, credit_minor, currency, entity_id, invoice_id, payment_id` | K1 |
| D05 | `invoices.jsonl`: `doc_id, invoice_id, entity_id, issued_at, due_at, currency, total_minor, line_items` | K1 |
| D06 | `payments.jsonl`: `doc_id, payment_id, timestamp, currency, amount_minor, invoice_refs` | K1 |
| D07 | `fx.csv`: `date, source_currency, target_currency, rate` | K1 |
| D08 | `policy.json`: выбор даты курса, границы периода, округление | K1 |
| D09 | Отсутствующие ссылки — явные `null`, а не угаданные связи | K1 |
| D10 | `truth.json`: `issue_id, type, affected_ids, expected_amount_minor, currency`, допустимые наборы доказательств. `provenance.json`: история генерации и внесённых изменений | K2 |
| D11 | Агент не видит `truth.json`, `provenance.json` и seed. Оценщик работает вне процесса агента. Записи доступны только на чтение через узкий интерфейс | K1, блокер |
| D12 | Эталон не утекает через наблюдения, пути, ошибки, debug info и объяснения награды во время закрытого прогона | K1, блокер |

### Контракт среды (раздел 04)
| Код | Требование | Критерий |
|---|---|---|
| E01 | `reset(seed, config)` возвращает `(observation, info)`. Первое наблюдение: задача, manifest, краткая политика, остаток бюджета | K1 |
| E02 | `step(action)` возвращает `(observation, reward, terminated, truncated, info)`, всё JSON-совместимо | K1 |
| E03 | Одинаковые seed, config, версия и действия воспроизводят записи, переходы и награды. `reset` изолирует состояние эпизода | K4 |
| E04 | Действия: `list_records(table, cursor, limit)`, `get_record(table, id)`, `get_document(doc_id)`, `calculator(expression)`, `submit(findings)` | K1 |
| E05 | Страница — максимум 50 строк, курсоры стабильны | K1 |
| E06 | Калькулятор допускает только арифметику и десятичные числа, не код и не файлы | K1 |
| E07 | Неизвестный ID или действие даёт ограниченную ошибку и расходует шаг | K1 |
| E08 | Наблюдение содержит только запрошенные записи, результат или ошибку и остаток шагов. Нет shell, SQL, файловой системы, интернета | K1 |
| E09 | Максимум 100 шагов, включая отправку. `submit` завершает эпизод с `terminated=true` | K1 |
| E10 | Лимит шагов или времени даёт `truncated=true` и пустой итоговый ответ | K1 |
| E11 | За исследование награда нулевая. Подсказок о правильности по ходу нет | K1, K3 |
| E12 | Терминальная награда возвращается политике только в открытом режиме обучения. При проверке награда и диагностика остаются у оценщика до конца прогона | K1 |

### Выводы и награда (раздел 05)
| Код | Требование | Критерий |
|---|---|---|
| S01 | `submit` принимает `{episode_id, findings: [{type, affected_ids, claimed_amount_minor, currency, evidence_ids, explanation}]}` | K1 |
| S02 | Лимиты: максимум 30 выводов, 10 ID доказательств и 1 000 символов объяснения на вывод | K1, K3 |
| S03 | Неверная структура завершает эпизод с наградой −1 и ошибкой в журнале оценщика | K3 |
| S04 | Сопоставление с эталоном взаимно однозначное. TP требует правильного типа, канонических `affected_ids`, суммы в явно указанном допуске, валюты и хотя бы одного полного допустимого набора доказательств | K3 |
| S05 | Несопоставленные и повторные выводы — FP. Пропущенные эталонные ошибки — FN. Повтор не приносит баллов | K3 |
| S06 | Код нормализации, допусков и выбора при неоднозначном совпадении опубликован | K3 |
| S07 | `P=TP/(TP+FP)`, `R=TP/(TP+FN)`, `F1=2TP/(2TP+FP+FN)`. При нулевом знаменателе P или R равны 0. Эталон и выводы пусты → `F1=1`. Эталон пуст, выводы есть → `F1=0` | K3 |
| S08 | Терминальная награда = `clip(2*F1 − 1 − 0.002*inspection_steps, −1, 1)`. Экспериментальную можно добавить, но общую сохранить и показывать отдельно | K3 |
| S09 | Награда зависит от полей и доказательств, а не от убедительного текста | K3 |
| S10 | Тесты показывают: верный полный ответ лучше молчания на ошибочных книгах; молчание лучше ложных обвинений на чистых; дубли не дают выгоды; пометка всех строк и типов даёт плохой результат; экономия шагов лишь немного различает равные ответы | K3 |
| S11 | Проверены: угаданные ID, неподтверждённые доказательства, валюты, повторная отправка, неверный ввод, тайм-аут | K3 |

## 8. Определения проверок жюри (опубликованы 20 ноября 2026)

Источник: [genesis-exe.com/fintech-checks.html](https://genesis-exe.com/fintech-checks.html). Ниже — наша сводка того, что меняет реализацию; при споре главнее страница организаторов. Баллы остаются 25/25/25/15/10.

**Как жюри подключается.** Через тонкий модуль `judge_adapter.py` в нашем контейнере: `generate_episode(seed, config, output_dir)`, `make_env()` с методами `reset(seed, config)` и `step(action)`, `score_episode(episode_dir, findings, inspection_steps)`. В закрытом режиме `reset` получает `{"mode": "closed", "episode_dir": ..., "team_config": ...}` и загружает именно этот каталог. Политики жюри работают в отдельном процессе и видят только наблюдения.

**Четыре блока.**
- Блок 1, C01–C20: контрактные тесты на фикстурах C (чистый эпизод), E (одна ошибка), L (таблица от 101 строки) и на ID U, которого нет в открытых данных.
- Блок 2, D01–D20: закрытые эпизоды нашего генератора по его документированной конфигурации. Пять чистых: обычная сверка, разбитый платёж, возврат, законные повторы сумм, граница курса или периода. Три с дублями, три с распределением (хотя бы один пропуск и один частичный случай), две с датой или курсом, две с периодом, три и два эпизода двух сценариев взаимодействия. Зачёт требует согласованных книг до внесения ошибки, именно заявленного расхождения после, полного доступного набора доказательств и форматов раздела 03.
- Блок 3, тесты 1–20 и открытые примеры M01–M12: matcher и награда на фикстуре с одной ошибкой A (одна запись, 10 000 KZT, доказательства {D1, D2}, допуск 0).
- Блок 4, P01–P20: жюри копирует эпизод, переставляет записи и (или) согласованно меняет ID во всех файлах, включая truth и provenance. Ответ oracle, TP/FP/FN, P, R, F1 и награда должны совпасть при одинаковом числе шагов.

**Соглашения, которые уточняют кейс.**
- `submit` — одно из 100 действий, но не входит в `inspection_steps`. Все прежние вызовы `step`, в том числе ошибочные, входят. `submit` сотым действием принимается.
- Лимит времени — 60 секунд от начала `reset`, включая работу политики.
- Неверный тип JSON-значения, отсутствующее поле или превышение лимита — структурная ошибка всего ответа (−1). Структурно правильный вывод с неверным типом ошибки, ID, суммой, валютой или доказательством — FP.
- ID и валюта сравниваются точно, без смены регистра и обрезки пробелов. `affected_ids` и `evidence_ids` — множества после проверки лимитов по исходным спискам.
- Вывод, который ссылается на несуществующий `evidence_id`, не сопоставляется.
- Допуск суммы по умолчанию 0. Ненулевой допуск фиксирован для типа и опубликован заранее.
- Выбор при равных сопоставлениях: эталонные `issue_id` по возрастанию code points, затем лексикографически наименьшая последовательность пар (`issue_id`, индекс вывода).

| Код | Требование | Критерий |
|---|---|---|
| J01 | `judge_adapter.py` с `generate_episode`, `make_env` (`reset`/`step`) и `score_episode` по интерфейсу жюри | K1–K4 |
| J02 | Оболочка действия `{"name", "args"}`. Наблюдения: первое — `{task, manifest, policy, remaining_steps}`, далее — `{result, error, remaining_steps}`. Результаты: `list_records` → `{records, next_cursor}`, `get_record`/`get_document` → объект, `calculator` → десятичная строка, `submit` → `{"accepted": true}` | K1 |
| J03 | Закрытый `reset` загружает каталог эпизода как есть и при повторе начинает его заново. `train` генерирует эпизод из `seed` и `team_config`; терминальная награда доступна политике только в нём | K1, K4 |
| J04 | `score_episode` возвращает `tp, fp, fn, precision, recall, f1, return`. Для невалидного ответа `return = −1`, остальные `null`, ошибка в журнале оценщика | K3 |
| J05 | 60 секунд от начала `reset`. Шаг после лимита не выполняется, эпизод завершается с `truncated=true` и пустым ответом | K1 |
| J06 | Соглашения matcher выше: что структурно, что FP, точное сравнение, несуществующие доказательства, допуск | K3 |
