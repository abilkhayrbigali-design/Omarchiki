# Доменная модель v1

Общий контракт для генератора, независимого решателя, matcher и базовых политик. Всё здесь — решения версии 1; если определения проверок организаторов им противоречат, меняем здесь и только потом в коде.

Главная идея: **ожидаемые книги — чистая функция от документов, курсов и политики.** Ошибка — это расхождение фактической книги с ожидаемой. Ожидаемые суммы никогда не выводятся из других строк книги, поэтому одна ошибка не порождает цепочку вторичных.

## 1. Мир

- Одна вымышленная компания, один отчётный период `[period_start, period_end)`. Конец периода не включается.
- Часовой пояс компании — **фиксированное смещение** (`+05:00`), без IANA-зон и перехода на летнее время. Причина: база tzdata меняется от версии к версии и ломает воспроизводимость.
- Базовая валюта и 1–3 иностранные. Разрядность валют разная: есть валюты с 2 знаками и хотя бы одна с 0 знаков.
- Компания продаёт клиентам: выставляет счета и получает платежи. Закупки в v1 не моделируем.
- Банковский счёт только в базовой валюте. Иностранный платёж конвертируется при поступлении.
- Записи покрывают период с запасом в несколько недель с обеих сторон, иначе ошибка отнесения к периоду невозможна.

## 2. Документы

**Счёт** (`invoices.jsonl`): `doc_id, invoice_id, entity_id, issued_at, due_at, currency, total_minor, line_items`.
- `line_items[]`: `description, quantity, unit_price_minor, amount_minor, order_ref, service_period`.
- `order_ref` — ссылка на заказ. Правило политики: на один `order_ref` приходится один счёт.
- Счёт с отрицательным `total_minor` — кредит-нота (возврат).

**Платёж** (`payments.jsonl`): `doc_id, payment_id, timestamp, currency, amount_minor, invoice_refs`.
- `invoice_refs` — список `invoice_id` в порядке, указанном плательщиком, или `null`, если платёж без назначения.
- Отрицательный `amount_minor` — возврат денег клиенту, ссылается на кредит-ноту.

**Курсы** (`fx.csv`): `date, source_currency, target_currency, rate`. Одна единица исходной валюты равна `rate` единиц целевой. Курс есть на каждый календарный день диапазона. ID строки для `get_record`: `YYYY-MM-DD/SRC/TGT`.

Все ID уникальны глобально, между таблицами тоже.

## 3. План счетов

Роли счетов и их коды перечислены в `policy.json`.

| Роль | Валюта строк | Назначение |
|---|---|---|
| `CASH` | базовая | банковский счёт |
| `AR` | валюта счёта | дебиторская задолженность |
| `REVENUE` | валюта счёта | выручка |
| `UNAPPLIED` | валюта платежа | поступления без назначения |
| `FX_CLEARING` | обе | переходный счёт конвертации |
| `EXPENSE` | базовая | фоновые расходы, не связаны с документами |

## 4. Правила проводок

Каждая строка книги — в валюте из своего столбца `currency`. Проводка — группа строк с общим ключом: `payment_id`, если он есть; иначе `invoice_id`; иначе `timestamp`. Все строки проводки имеют один `timestamp`.

**Счёт** на сумму `T` в валюте `c`: дебет `AR` `T`, кредит `REVENUE` `T`. Для кредит-ноты стороны меняются местами.

**Платёж** на сумму `A` в валюте `c`:
1. Распределение по правилу `listed_order_up_to_open_balance`: платежи обрабатываются по времени; сумма идёт на счета из `invoice_refs` в указанном порядке, на каждый не больше его открытого остатка. Остаток считается по документам, а не по книге.
2. Кредит `AR` на каждую распределённую часть с `invoice_id` и `payment_id`. Нераспределённый остаток — кредит `UNAPPLIED` с `invoice_id = null`.
3. Если `c` — базовая валюта: дебет `CASH` `A`.
4. Иначе: дебет `FX_CLEARING` `A` в валюте `c`; кредит `FX_CLEARING` `B` и дебет `CASH` `B` в базовой, где `B = round(A × 10^(e_base − e_c) × rate)`. Дата курса и режим округления берутся из `policy.json`.

**Дата курса** — из документа, а не из проводки. Варианты политики: локальная дата платежа; предыдущий день; дата по UTC.

**Время проводки** может отставать от времени документа, но в чистых книгах проводка всегда в том же периоде, что и документ.

Генератор гарантирует, что платежи на один счёт имеют разные моменты времени. Порядок при равном времени не определяется через ID.

## 5. Инварианты чистых книг

| Код | Равенство |
|---|---|
| I1 | В каждой проводке и в книге целиком сумма дебета равна сумме кредита по каждой валюте. В строке ненулевая ровно одна сторона |
| I2 | `total_minor` счёта равен сумме `amount_minor` его строк; `amount_minor = quantity × unit_price_minor` |
| I3 | У каждого счёта ровно одна проводка признания на сумму `total_minor` в его валюте |
| I4 | Проводка документа находится в том же периоде, что и дата документа в поясе компании |
| I5 | У каждого платежа кредиты `AR` и `UNAPPLIED` совпадают с распределением по правилу из раздела 4 |
| I6 | Для иностранного платежа сумма `CASH` равна конвертации по курсу на дату из политики |
| I7 | На один `order_ref` один счёт; `invoice_id` не повторяется в разных документах |

До внесения ошибок выполняются все семь. Каждая ошибка нарушает заранее известные инварианты на заранее известную сумму.

## 6. Типы ошибок

| `type` | Нарушает | Что происходит | `affected_ids` (канон) | Сумма и валюта |
|---|---|---|---|---|
| `duplicate_invoice` | I3, I7 | Счёт внесён повторно и проведён ещё раз. Варианты: тот же `invoice_id` во втором документе; другой `invoice_id` при том же `order_ref` и тех же строках | `doc_id` всех копий группы | `(k − 1) × |total_minor|`, валюта счёта |
| `payment_allocation` | I5 | Платёж не разнесён на счёт совсем, разнесён частично или разнесён на другой счёт | `doc_id` платежа и `doc_id` счёта | недораспределённая сумма, валюта платежа |
| `fx_conversion` | I6 | Иностранный платёж сконвертирован по курсу не той даты или не той валютной пары | `doc_id` платежа | `|CASH факт − CASH ожидаемо|`, базовая валюта |
| `period_cutoff` | I4 | Проводка документа попала в другой период, чем сам документ | `doc_id` документа | `|сумма документа|`, валюта документа |

**Гранулярность.** Один вывод — одно нарушенное правило на одном субъекте. Для распределения субъект — пара платёж + счёт. Пара `(type, affected_ids)` уникальна в эпизоде.

**Допуск суммы.** Ноль для всех типов, кроме `fx_conversion`: там `policy.tolerances.fx_conversion_minor`, по умолчанию 1.

**Нет серой зоны.** Внесённое расхождение не меньше 100 минимальных единиц своей валюты; у чистых записей расхождение ровно ноль. Поэтому решатель сообщает о любом ненулевом расхождении.

### Уточнения, обязательные для генератора и решателя

- **Валюта платежа.** Платёж ссылается только на счета в своей валюте.
- **Порядок платежей.** Платежи, ссылающиеся на один и тот же счёт, имеют разные моменты времени.
- **Счёт для распределения.** Остаток по `invoice_id` считается от его документа один раз. Если у `invoice_id` несколько документов (дубль с тем же `invoice_id`), документом счёта считается тот, у которого самый ранний `issued_at`; у копий в одной группе `issued_at` всегда разный. Ошибки распределения на `invoice_id` с несколькими документами генератор не создаёт.
- **Фактически распределённое.** Сумма кредитов `AR` с данными `payment_id` и `invoice_id` (для возвратов — дебетов). Строка `UNAPPLIED` с `invoice_id = null`.
- **Фактическая конвертация.** Сумма `debit − credit` строк `CASH` с данным `payment_id`. Ожидаемая — конвертация `amount_minor` платежа по политике, со знаком.
- **Проводка документа.** Строки счёта — строки с его `invoice_id` и `payment_id = null`. Строки платежа — строки с его `payment_id`. У всех строк проводки один `timestamp`.
- **Перерасход** на другой счёт отдельной ошибкой не считается: это «куда ушла сумма» для недополучившего счёта.
- **Достаточность набора для распределения.** Ошибка распределения вносится только туда, где счёт стоит первым в `invoice_refs` платежа и во всех более ранних платежах, ссылающихся на него. Тогда ожидаемая сумма зависит только от документов набора.
- **Группа дублей** — документы, связанные общим `invoice_id` или общим `order_ref`, по цепочке (A~B~C — одна группа, k = 3). У копий одинаковые валюта и сумма и разный `issued_at`. Кредит-нота имеет свой `order_ref`. Копия с тем же `invoice_id` проведена в другой момент, чем оригинал: строки одного `invoice_id` делятся на проводки по моменту времени.
- **Классы периода** три: до, внутри, после отчётного периода. Отсечка — документ и его проводка в разных классах. Границы периода — локальная полночь в поясе компании.
- **Ограничения данных.** Платежи в один момент ссылаются на непересекающиеся счета. Нулевых сумм нет. Строки без документа — только `EXPENSE` и `CASH` в базовой валюте, сбалансированные на каждый момент. На строках `UNAPPLIED`, `CASH`, `FX_CLEARING` `invoice_id = null`. Положительный платёж не ссылается на кредит-ноту, возврат — на обычный счёт. Чистая переплата уходит на `UNAPPLIED`.
- **Конвертация** — всегда пара «валюта платежа → базовая». Округление `half_up` — от нуля, со знаком.

### Решения генератора (версия 0.2.0)

- **Область аудита.** Ошибки вносятся только в записи отчётного периода: дата документа или его проводка внутри периода. Записи в неделях вокруг периода — контекст и ловушки (`policy.scope`).
- **Виды периода.** Календарный месяц (60 %), квартал (20 %), фискальный период в 4 или 5 недель с произвольной локальной полуночи (по 10 %). Границы — локальная полночь в поясе компании.
- **I3 считается по `invoice_id`.** Дубль с тем же `invoice_id` нарушает I3 и I7, дубль с новым `invoice_id` — только I7. I5 сообщает только о недораспределении.
- **Чистые проводки** лежат в том же классе периода, что и документ, но могут переходить через границу календарного месяца внутри периода.
- **Отсечка** всегда — поздняя проводка через границу периода: документ за 0–3 дня до начала или конца, проводка через 0–3 дня после неё. Задним числом проводки не вносятся.
- **Ошибки только на обычных записях.** Ловушки, кредит-ноты и возвраты ошибок не несут.
- **Распределение.** Ошибки — на первом платеже, на последующих взносах (ожидаемое = открытый остаток) и на платежах с несколькими ссылками, где счёт стоит первым; во всех случаях счёт первый в ссылках этого и всех более ранних платежей, более ранних платежей не больше трёх. Варианты: «нет» (сумма уходит на `UNAPPLIED`), «частично», «на другой счёт».
- **Копия-дубль** сохраняет срок оплаты оригинала: `due_at` = дата копии + срок.
- **Ошибочный курс** берётся в пределах недели и только если разница не меньше max(100 минимальных единиц, 0,5 % правильной суммы).
- **Размер.** Число счетов попадает в диапазон `size.invoices`; ловушки, носители ошибок, копии и обычные счета считаются вместе. Если ошибки и ловушки не помещаются, генерация сразу отклоняется с `CapacityError`. Валюта с 0 знаков после запятой есть в пуле, но не обязательна в каждом эпизоде.

### Допустимые наборы доказательств

Вывод засчитывается, если его `evidence_ids` содержат целиком хотя бы один набор. Лишние ID допустимы, общий лимит 10 защищает от перечисления всего подряд. По записям набора, манифесту и политике сумма и тип пересчитываются заново.

| `type` | Набор |
|---|---|
| `duplicate_invoice` | `doc_id` всех копий |
| `payment_allocation` | `doc_id` платежа + `doc_id` счёта + `row_id` всех строк проводки платежа в валюте платежа (`CASH` или `FX_CLEARING`, `AR`, `UNAPPLIED`) + `doc_id` более ранних платежей, ссылающихся на этот счёт. Генератор держит набор в пределах 10 ID |
| `fx_conversion` | `doc_id` платежа + `row_id` строки `CASH` этого платежа + ID строки правильного курса. Второй набор — то же со строкой `FX_CLEARING` в базовой валюте вместо `CASH` |
| `period_cutoff` | `doc_id` документа + `row_id` любой одной строки его проводки (по набору на строку) |

Каждый набор не длиннее 10 ID и состоит только из открытых записей. Требование **независимой достаточности**: по записям одного набора, манифесту и политике тип и сумму ошибки можно пересчитать заново. Это проверяет `verify/evidence.py`.

## 7. Взаимодействующие сценарии

| Сценарий | Суть | Что в эталоне |
|---|---|---|
| `fx_partial_at_boundary` | Иностранный платёж у границы периода: проведён по другую сторону границы, сконвертирован по курсу даты проводки вместо даты документа и разнесён на счёт частично | `period_cutoff` + `fx_conversion` + `payment_allocation` на одном платеже |
| `duplicate_misallocated` | Счёт задвоен под другим `invoice_id`; платёж ссылается на оригинал, а разнесён на копию | `duplicate_invoice` на обеих копиях + `payment_allocation` на паре платёж + оригинал |

Суммы каждой ошибки считаются от документов независимо от остальных, поэтому неоднозначности нет. Сложность в рассуждении: наивная проверка находит одну ошибку и останавливается.

Вне этих сценариев один документ участвует не больше чем в одной внесённой ошибке.

## 8. Отвлекающие случаи

Корректны по построению. Независимый решатель обязан не найти в них ничего.

| Код | Случай | Против какого трюка |
|---|---|---|
| X1 | Один счёт оплачен двумя-тремя платежами | «платёж меньше счёта — ошибка» |
| X2 | Один платёж на несколько счетов | «у платежа одна строка AR» |
| X3 | Законная частичная оплата, счёт остаётся открытым | «незакрытый счёт — ошибка» |
| X4 | Кредит-нота и возврат денег | «отрицательная сумма — ошибка» |
| X5 | Подписка: один клиент, одна сумма каждый месяц, разные `service_period` и `order_ref` | «одинаковая сумма у клиента — дубль» |
| X6 | Два разных заказа одного клиента на одну сумму в один день | то же |
| X7 | Платёж без назначения, корректно на `UNAPPLIED` | «UNAPPLIED — ошибка» |
| X8 | Документ у границы периода, записанный с другим смещением: по UTC дата одна, по поясу компании другая | сравнение дат строкой или по UTC |
| X9 | Иностранный платёж в день резкого скачка курса, сконвертирован верно | «большая курсовая разница — ошибка» |
| X10 | Проводка отстаёт от документа на дни, но в том же периоде | «время не совпало — ошибка» |

## 9. Правила эталона

- T1. Ожидаемые значения считаются только от документов, курсов и политики.
- T2. Пара `(type, affected_ids)` уникальна. Гранулярность фиксирована разделом 6.
- T3. У каждой ошибки есть хотя бы один набор доказательств, и он проходит проверку независимой достаточности.
- T4. Ничего в семантике не зависит от строк ID и порядка записей.
- T5. Вне эталона расхождений нет: решатель по открытым данным возвращает ровно эталон.
- T6. Публичные данные — функция от множества записей, а не от порядка генерации. Внесённая запись неотличима по позиции, формату ID, округлости суммы и точности времени.
